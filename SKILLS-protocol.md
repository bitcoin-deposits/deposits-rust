# SKILLS — protocol mechanics and investigation

How the protocol actually works on the wire, and how to investigate when something looks wrong. Companion to [SKILLS-wallet.md](SKILLS-wallet.md) (depositor) and [SKILLS-operator.md](SKILLS-operator.md) (operator).

The DEPs ([DEP-01](DEP-01.md) onward) are the normative reference. This doc is the working knowledge — what to recompute, where to grep, what an event actually contains.

---

## 1. Mental model in three sentences

A **ledger** is an append-only hash chain of signed updates. Each update carries a TLV-encoded message describing one operation (a deposit, a transfer, a quorum change, …) plus cosignatures from a majority of the current quorum. Funds live in a Bitcoin Taproot UTXO whose script paths enforce the same trust model the chain encodes: majority of cosigners can spend immediately; the operator alone needs to wait weeks.

The chain is public. Wallets validate end-to-end against the relay; the operator is not trusted, only watched.

For a fuller introduction, [book/02-mental-model.md](book/02-mental-model.md) is a good walkthrough.

## 2. Anatomy of a signed update

A `SignedLedgerUpdate` (Kind 9100) carries:

| Field | Source |
|---|---|
| `seq` | u64, increments per update |
| `prev_hash` | `content_hash` of the previous update (32 bytes) |
| `message` | TLV-encoded operation (the actual op) |
| `signatures` | Operator BIP-340 over `content_hash` |
| `cosignatures` | Vec of (cosigner_pubkey, member_ledger_hash, sig) — the cosigner's view of *their own* ledger at signing time, plus their BIP-340 over `content_hash` |
| `content_hash` | `sha256(seq_le ‖ prev_hash ‖ message ‖ cosig_triples)` — derived, not on the wire |

**`content_hash` is wire-derived.** The TLV does not transmit it; receivers recompute via `compute_hash()`. Hand-rolling SHA-256 in tools means hand-rolling the exact concatenation order — easier to use the helper. (Memory: `feedback_signed_update_content_hash.md`.)

**Cosignatures are dual-purpose.** Each cosigner's `member_ledger_hash` is the chain head of *their* ledger when they signed. This proves they were online and synced; it also lets fraud-proof verifiers tie a cosignature back to a specific ledger (so a misbehaving cosigner's collateral can be slashed).

## 3. Anatomy of an operation (TLV)

A `message` is TLV. First byte is the **discriminant** (which operation), then varint-headed `(tag, length, value)` tuples.

| Discriminant | Operation | Where defined |
|---|---|---|
| 1 | `LedgerOpen` | DEP-02 §LedgerOpen |
| 12 | `QuorumBegin` | DEP-03, DEP-05 |
| 20 | `DepositOpen` | DEP-08 |
| 21 | `DepositClose` | DEP-08 |
| 22 | `FeeChange` | DEP-07 |
| 30 | `InvoiceCredit` | DEP-08 |
| 31 / 32 / 33 | `InvoiceLock` / `InvoiceFail` / `InvoiceFulfill` | DEP-08 |
| 35 / 36 / 37 / 38 | `OnchainCredit` / `OnchainLock` / `OnchainFail` / `OnchainFulfill` | DEP-08 |
| 43 / 44 / 46 | `QuorumAddMember` / `QuorumRemoveMember` / `QuorumJoin` | DEP-05 |
| 54 | `DisputeEnter` | DEP-06 |
| 55 / 56 / 57 | `DisputeAcquire` / `DisputeYield` / `DisputeArmed` | DEP-06 |
| 60 | `LedgerClose` | DEP-02 |
| 70 / 71 | `TransferLock` / `TransferComplete` | DEP-09 |

Full discriminant + tag table: `deposits-protocol/deposits_protocol.ksy` and `DEP-02.md`. The kaitai schema is the canonical doc; `tlv-catalog.js` (auto-generated by `bin/gen-tlv-catalog.sh`) is what the explorer renders.

**TLV tags are global.** Tag 6 is `quorum_members` whether it appears in `QuorumBegin` or anywhere else. New fields get new tags; reused tags must mean the same thing. The 2026-05 addition of `quorum_member_ledger_ids` (tag 276) is parallel to tag 6 — same length, same order, paired by index — so verifiers and explorers can resolve cosigner ledgers without walking history.

## 4. The hash chain

```
content_hash[i] = sha256( seq_le ‖ prev_hash ‖ message ‖ cosig_triples )
prev_hash[i+1] = content_hash[i]
```

`content_hash` of the very first update (`LedgerOpen`) sets `prev_hash` to 32 bytes of zeros.

**Verifying an update offline:**

```bash
python3 deposits-tools/bin/decode-update.py < update.json
```

It decodes the TLV, recomputes `content_hash`, and prints intermediate values. If the recomputed hash doesn't match what `prev_hash` expects on the next update, you've found a tampered chain.

**Replaying a whole ledger:**

```bash
deposits-tools/bin/replay-ledger.sh <ledger_id>
```

Pulls every Kind 9100 from the relay, sorts by `seq`, validates the chain end-to-end. This is how the wallet's `ledger validate` works internally.

## 5. BIP-340 verification

Every signed thing in the protocol is BIP-340 (Schnorr xonly). Three places to verify:

| Signature | Signer | Message |
|---|---|---|
| Operator signature on update | Operator npub | `content_hash` |
| Cosignature on update | Cosigner npub | `content_hash` |
| Invoice cosignature | Operator + each cosigner | Tagged hash `invoice_cosign_signing_message` over BOLT11 |

The web explorer's per-update view does all three client-side. For offline verification, `decode-update.py` prints the message bytes and you can `secp256k1` it yourself.

**Tagged hashes.** Some signatures use BIP-340 tagged hashes (e.g. invoice cosign). Tag string matters; it's a domain separator. Don't roll your own with the wrong tag.

**Where signatures come from doesn't affect verification.** Production operators may run `deposits-signer` as a separate process (see [SIGNER.md](SIGNER.md)); the daemon talks to it over a Unix socket and never holds the operator-protocol secret. Receivers see only the resulting BIP-340 sig and verify against the operator's pubkey from the ledger — the wire protocol is unchanged. `deposits-signer-api::Signer` is the trait through which every protocol-level operator/cosign sig flows in the daemon.

**Operator pubkey vs. Nostr publisher pubkey.** When an operator runs with a separate signer, the daemon holds a *Nostr identity* secret distinct from the operator-protocol key (sibling derivation at `m/85'/0'/0'/0/0` vs `m/86'/0'/0'/0/0`). Kind 9100 / 39100 events are published under the Nostr pubkey; the operator's protocol pubkey appears in event *content* (e.g. `LedgerOpen.operator_id`, advertisement content). Verifiers should always check `operator_signature` against the operator pubkey from the ledger, not the event's outer `pubkey`.

## 6. Cosignatures and member ledgers

Each cosignature triple is `(cosigner_pubkey, member_ledger_hash, signature)`. Resolving "which ledger's chain-head is `member_ledger_hash`?" has two tiers (memory: explorer Stage C):

1. **Tier 1 (since 2026-05):** Most recent `QuorumBegin`'s `quorum_member_ledger_ids` — pubkey at index `i` pairs with member_ledger_id at index `i`.
2. **Tier 2 (fallback):** Walk the operator's ledger history for `QuorumAddMember` ops; each carries the (pubkey, member_ledger_id) pair directly.

Once you have the member_ledger_id, fetch the cosigner's ledger and find the update whose `content_hash == member_ledger_hash`. The explorer's `findEventByContentHash` does this — fetches the cosigner's events and recomputes content_hash on each.

This linkage is what makes a cosigner's slashing actually slashing: their collateral is in *their* ledger, identified at every signing point, not just hand-waved.

## 7. Reserves and collateral on-chain

A ledger's UTXO is one Taproot output containing both reserves (deposit capacity) and collateral (security bond). Spending paths are tiered (DEP-03):

| Tier | Signers | Timelock |
|---|---|---|
| 0 | Majority of quorum (no operator) | Immediate |
| 1 | Minority of quorum (no operator) | 1008 blocks (~1 week) |
| 2 | Operator only | 2016 blocks (~2 weeks) |
| 3 | Any single party | 4032 blocks (~4 weeks) |

The operator is **deliberately excluded from Tier 0 and 1** — the quorum can recover reserves without operator participation. The internal key is BIP-341 NUMS (no key-path spend possible).

`QuorumBegin.spending_txid` and `new_outpoint_(txid|vout)` anchor the chain to a real on-chain output; cosigners verify `value == reserves_amount + collateral_amount` and minimum confirmations before signing the first `QuorumBegin`. Defaults: 6 mainnet, 3 testnet/signet, 1 regtest.

`QuorumBegin` rotations include an `OP_RETURN <chain_hash>` in the transaction — an on-chain anchor a wallet can use to verify relay state hasn't been censored.

## 8. Disputes and the custody lottery

Every dispute starts with a fraud proof. Six types currently:

| Type | Class | Trigger |
|---|---|---|
| `QuorumExpired` | Respectful | Operator failed to rotate before `quorum_expiry` |
| `UncreditedOnchainPayment` | Punitive | Operator received on-chain payment, didn't credit |
| `UncreditedLightningPayment` | Punitive | Operator received Lightning payment, didn't credit |
| `StaleCosignature` | Punitive | Cosigner backdated `member_ledger_hash` |
| `DisputeDereliction` | Punitive | Cosigner ignored a fraud proof in window |
| `NonConformingUpdate` | Punitive | Operator signed a protocol-violating update |

Class determines confiscation tx shape and cross-ledger propagation:

- **Respectful** doesn't propagate. Operator gets `(reserves - obligations) + collateral` back as change; lottery winner gets `obligations`.
- **Punitive** propagates to the operator's other ledgers. Full UTXO → confiscation; reserves of `obligations` to winner; the rest split equally among the `Q` cosigners. Winner provides fresh collateral when claiming.

**Custody lottery.** `(sum_of_contributions) mod N` picks the winner; the script enforces it. Each disputant's preimage length contributes 1..=N to the sum. See [CUSTODY_LOTTERY.md](CUSTODY_LOTTERY.md) for the full script-tree design.

**Late-discovered equivocation** (memory: `project_equivocation_late_discovery.md`) is "as of now" — the chain doesn't rewind on discovering a conflicting `U_B`; the conflicting update is fraud-proof evidence, slashing the response.

## 10. Investigation playbook

**"My balance is wrong."**
1. `deposits-wallet ledger validate <ledger_id>` — does the chain validate?
2. If yes, walk every op affecting your deposit (`ledger show` filtered to your pubkey). The state machine in `deposits-core/src/ledger.rs` is the authoritative balance computation.
3. If validation fails, the chain is tampered or partial. Try a different relay; if multiple relays disagree, you've found an equivocation.

**"This update won't validate."**
1. `decode-update.py` — does TLV parse cleanly?
2. Recompute `content_hash` and compare to `prev_hash` of the *next* update. Mismatch means tampering.
3. BIP-340 verify the operator sig against the recomputed hash. Mismatch means forged signature.
4. For each cosignature: verify the sig, then fetch the cosigner's ledger and confirm `member_ledger_hash` is one of their actual chain-heads. Mismatch is `StaleCosignature` — fraud proof material.

**"Where did the funds go?"**
1. `deposits-wallet ledger custody <ledger_id>` traces rotations, disputes, and acquisitions.
2. Each `QuorumBegin` carries `spending_txid` and `new_outpoint_(txid|vout)`. Walk those on-chain.
3. If a `DisputeAcquire` is in the chain, the funds went to the lottery winner; their `claim_txid` references the lottery output's confiscation transaction.

**"Cosign timeout in production."**
Per memory: `project_phase4_cosign_blockers`, `feedback_deposit_credit_unique_invoice`. Three causes, walk in order:
1. Members not subscribed to the operator's ledger relay (subscription dropped).
2. Txid byte-order mismatch in `QuorumBegin` (display vs internal).
3. Duplicate `invoice_id` → duplicate `payment_hash` → cosigners reject as `duplicate_credit`.

**"This advertisement looks wrong."**
1. Kind 39100 is replaceable — check timestamps; you may be seeing a cached/old copy.
2. Verify operator signature on the advertisement.
3. `minimum_fees` is annualized; divide by `52560 / fee_period_blocks` to get per-period.

**"I think there's an equivocation."**
1. Two Kind 9100 events at the same `seq`, same operator, different `content_hash`.
2. `nostr-broadcast.sh` to publish the proof if it's not already on relay.
3. Memory: late-discovered equivocation slashes "as of now," not retroactively. The chain doesn't rewind.

## 11. Adding a TLV field (the walkthrough)

1. Pick a tag number. Constants are in `deposits-protocol/src/messages/tlv_codec.rs`. Pick one not already used; convention is to leave gaps so related fields can cluster.
2. Add the field to the corresponding `types.rs` struct.
3. Encode + decode in `tlv_codec.rs`. If it's optional or additive, make it skippable on decode.
4. Update the kaitai schema: add the field to the relevant `seq:` block in `deposits_protocol.ksy`, and add a comment in the TLV reference comment block — the catalog generator parses these comments.
5. Update `DEP-02` (wire format table) and the relevant DEP for the operation it touches (e.g. DEP-03/05 for `QuorumBegin`).
6. `bash deposits-tools/bin/gen-tlv-catalog.sh` regenerates `deposits-web/wallet/tlv-catalog.js`.
7. `cargo test -p deposits-protocol --test ksy_catalog_test --test kaitai_roundtrip` will catch a missing ksy entry or a roundtrip break.

The 2026-05 addition of `quorum_member_ledger_ids` (commit 61faf99) is a worked example of an additive parallel field — useful as a template.
